High-Level Architecture

What is this system?

An automated phone-based booking system for small service businesses (e.g. car detailing, cleaning). Customers call a number, navigate an IVR menu using keypad or voice, and can book, reschedule, cancel, or get quotes — all without a human operator.

Design Principle: Deterministic Core, AI at the Edges

Key Architectural Decision All business-critical logic (quote calculation, booking creation, cancellation) uses deterministic code — no AI. AI (Ollama) is only used at the edges for speech normalisation and off-script fallback. This ensures the system is auditable, predictable, and debuggable.

Detailed Component Breakdown

Twilio — Why not just use a SIP server?

Twilio abstracts the entire telephony infrastructure. Instead of managing SIP trunks, codecs, and carrier agreements, you write a webhook. Twilio calls your URL on every keypress or speech event. Alternatives like Vonage (Nexmo) or Plivo exist but Twilio has the best developer experience, global coverage, and a generous trial tier.

Twilio ConceptWhat it means
TwiMLXML dialect Twilio reads to control the call. You return it from your webhook.
<Gather>Collects DTMF digits (keypad) or speech. Fires your webhook when done.
<Say>Text-to-speech. Twilio reads it aloud to the caller.
<Hangup>Ends the call.
CallSidUnique ID for every call. Used to track state across multiple webhooks.
Twilio SignatureHMAC-SHA1 hash proving the request is genuinely from Twilio (security).

Node.js + Express — The Webhook Brain

Every time a caller presses a key or speaks, Twilio sends a POST to /webhook/twilio. Express handles it in milliseconds and returns TwiML. The state machine is implemented as a giant routeState() function that reads current_state from the database and branches accordingly.

PostgreSQL — Source of Truth

Nine tables capture everything: businesses, services, customers, bookings, calls, booking events, availability rules, notifications, and callback requests. Every state transition is persisted, so if a caller hangs up and calls back, the system can resume correctly.

n8n — Workflow Automation Without Code

n8n is a visual workflow builder. It handles tasks that run outside the live call: quote calculations, daily reminder emails, provider summaries at 4:30 PM, and booking confirmation emails. These don't need sub-second latency so they're better outside the Express server.

Calendly API — Availability Slots

The system reads Calendly's scheduled events to determine available time slots. When a customer calls, the system fetches the next available slots matching the requested service duration. Limitation: Calendly's API is read-only — it cannot create events. Bookings are stored in PostgreSQL only.

Next.js Dashboard — Provider Admin

A server-side rendered Next.js app giving the business owner visibility over all bookings, calls, callbacks, and services. It connects directly to PostgreSQL — no intermediate API needed since it's an internal tool.

For English press 1. Hindi ke liye 2...</Say> </Gather> Step 3: Caller presses 1 (English) → Twilio fires POST again: { Digits: "1", CallSid: "CA123" } → Express reads state = "LANGUAGE_MENU", Digits = "1" → Updates state to "MAIN_MENU_EN" → Returns 6-option main menu TwiML Step 4: Caller presses 1 (New Booking) → state = "MAIN_MENU_EN", Digits = "1" → Sets context.intent = "new_booking" → Updates state to "SERVICE_MENU_NEW" → Returns service list TwiML Step 5: Caller presses 1 (Exterior Wash) → Reads services from DB, maps keypad to service → Stores serviceId, serviceName in call context (JSONB) → Updates state to "COLLECT_REQUIRED_FIELDS" → Asks: "For a Sedan press 1, SUV press 2..." Step 6: Caller presses 1 (Sedan), then 1 (Standard) → Each answer stored in context JSONB → Calls n8n quote-engine webhook with service + vehicle + condition → n8n returns { quote_min: 290, quote_max: 410 } → State → "QUOTE_RESULT" → Reads: "Your quote is $290–$410. Press 1 for availability..." Step 7: Caller presses 1 (Check Availability) → Calls POST /api/availability → Fetches slots from Calendly API → Generates multilingual spoken labels → Returns top 3 slots: "For Tuesday May 5th at 9 AM, press 1..." Step 8: Caller presses 2 (selects 9 AM slot) → Slot stored in context (slotStart, slotEnd) → State → "CONFIRM_SLOT" → "You selected Tuesday 9 AM. Press 1 to confirm..." Step 9: Caller presses 1 (Confirm) → Conflict check: is this slot still free? → POST /api/bookings → upserts customer, inserts booking → Sends SMS confirmation via Twilio REST API → State → "END_CALL" → "Your booking is confirmed. Reference: abc-123. Goodbye!" Step 10: Twilio hangs up.

What Happens if Two People Book the Same Slot?

Race Condition — Handled by Conflict Check Before inserting any booking, the system runs a SQL overlap query: scheduled_start < $end AND scheduled_end > $start AND status = 'confirmed'. If a conflict exists, a 409 is returned and the IVR routes the caller back to pick a different time.

System Design Concepts

Scalability — Handling Thousands of Calls

ChallengeSolution
Many simultaneous callersExpress is stateless per request — each webhook is independent. Scale horizontally with a load balancer.
Call state across requestsState stored in PostgreSQL (not in memory). Any server can handle any webhook.
DB connection limitsConnection pool (pg Pool) — max 10 connections shared across all requests.
Slow Calendly APICache availability results for 30–60 seconds; callers in that window share the same response.
n8n becoming a bottleneckn8n handles async tasks (reminders, summaries) — never in the live call path for critical actions.

Fault Tolerance

Failure ScenarioHow it's handled
Calendly API is downFallback: generate slots from availability_rules table stored in PostgreSQL
Calendly cancel failsBest-effort — try to cancel, log error, continue. Booking is cancelled in DB regardless.
SMS fails to sendBooking is confirmed regardless. SMS failure is logged but doesn't block the caller.
DB is temporarily downExpress returns 500 → Twilio reads it as error, plays a generic "please try again" message
Caller hangs up mid-flowState is persisted at each step. If they call back, system resumes from last known state.
Twilio signature invalidMiddleware returns 403 — rejects the request before any state is changed

Latency Optimization

  • Twilio expects a TwiML response within 15 seconds — anything slower causes a timeout.
  • Most state transitions only hit the DB (single query) — sub-100ms response time.
  • Calendly API call (~300ms) only happens at the CHECK_AVAILABILITY state, not every webhook.
  • n8n quote engine call (~200ms) only at COLLECT_REQUIRED_FIELDS completion.
  • Database indexes on call_sid, caller_phone, status, scheduled_start ensure fast lookups.

Database Design — Why PostgreSQL over MongoDB?

Booking data is relational: a booking belongs to a customer, references a service, and belongs to a business. ACID transactions ensure that a booking is never half-written. The JSONB context column on the calls table gives us document-like flexibility for accumulating call state without schema changes.

Queue Systems

This system does not use a message queue (Redis/RabbitMQ) for the live call path because Twilio's webhook model is already asynchronous — each keypress is its own HTTP request. However, for a high-scale production system, reminder jobs should be moved to a queue (Bull + Redis) to decouple them from the n8n scheduler.

Webhook Handler — Core Logic

// Every Twilio event hits this handler
router.post('/', validateTwilio, async (req, res) => {
  const { CallSid, From, To, Digits, SpeechResult } = req.body;

  // 1. Find or create the call record
  let call = await pool.query(
    'SELECT * FROM calls WHERE call_sid = $1', [CallSid]
  );
  if (!call.rows.length) {
    call = await createNewCall(CallSid, From, To);
  }

  const state   = call.rows[0].current_state;  // e.g. "LANGUAGE_MENU"
  const context = call.rows[0].context;         // JSONB accumulation

  // 2. Convert speech to DTMF if needed
  const selected = mapSpeechToDigit(SpeechResult, state) || Digits;

  // 3. Route to correct state handler
  const twiml = await routeState(state, selected, context, call.rows[0]);

  // 4. Return TwiML XML
  res.set('Content-Type', 'text/xml');
  res.send(twiml);
});

State Machine Pattern

async function routeState(state, selected, context, callRecord) {
  switch (state) {
    case 'LANGUAGE_MENU':
      if (selected === '1') return transitionTo('MAIN_MENU_EN', callRecord);
      if (selected === '2') return transitionTo('MAIN_MENU_HI', callRecord);
      if (selected === '3') return transitionTo('MAIN_MENU_ZH', callRecord);
      return repeatMenu(state); // invalid input → repeat

    case 'MAIN_MENU_EN':
      if (selected === '1') return transitionTo('SERVICE_MENU_NEW', callRecord, { intent: 'new_booking' });
      if (selected === '2') return transitionTo('SERVICE_MENU_NEW', callRecord, { intent: 'check_availability' });
      // ... etc
  }
}

Security: Twilio Signature Validation

// middleware/twilioValidation.js
const twilio = require('twilio');

module.exports = (req, res, next) => {
  const signature = req.headers['x-twilio-signature'];
  const url       = process.env.WEBHOOK_BASE_URL + '/webhook/twilio';
  const authToken = process.env.TWILIO_AUTH_TOKEN;

  // Twilio signs every request with HMAC-SHA1
  if (!twilio.validateRequest(authToken, signature, url, req.body)) {
    return res.status(403).send('Forbidden');
  }
  next();
};
Why this matters in interviews Without signature validation, anyone who discovers your webhook URL can send fake calls and create bogus bookings. This is a classic security question interviewers ask.

AI Integration — Ollama (Planned Layer)

Honest project note Ollama is architected into the system but the current implementation uses keyword-regex matching instead. This is intentional — regex handles 95% of cases with zero latency. Ollama would add value for ambiguous multilingual input and truly off-script conversations.

What Ollama Does (and Why Local AI)

Ollama runs a local LLM (e.g. llama3.2) on the server, with no API calls to OpenAI. This means zero per-token cost, no data leaving the server, and predictable latency. For a small business IVR system, this is the right tradeoff.

Current Implementation: Keyword Regex

// Speech → DTMF mapping (deterministic, zero latency)
function mapSpeechToDigit(speech, state) {
  if (!speech) return null;
  const s = speech.toLowerCase();

  if (['MAIN_MENU_EN', 'MAIN_MENU_HI', 'MAIN_MENU_ZH'].includes(state)) {
    if (/\b(book|new booking|appointment)\b/.test(s))            return '1';
    if (/\b(availab|when|time|open|slot)\b/.test(s))             return '2';
    if (/\b(quote|price|cost|how much|estimate)\b/.test(s))      return '3';
    if (/\b(change|reschedule|move|different time)\b/.test(s))   return '4';
    if (/\b(cancel)\b/.test(s))                                  return '5';
    if (/\b(callback|call back|call me|message)\b/.test(s))      return '6';
  }
  return null; // unrecognised → repeat menu
}

Ollama Integration (How it Would Work)

// services/ollamaService.js
async function normaliseIntent(speechText, currentState, language) {
  const prompt = `
    The caller said: "${speechText}"
    Current IVR state: ${currentState}
    Language: ${language}

    Map this to one of these intents:
    1=new_booking, 2=check_availability, 3=get_quote,
    4=reschedule, 5=cancel, 6=callback, 9=repeat

    Respond with only the digit. If unclear, respond with "unclear".
  `;

  const response = await fetch('http://localhost:11434/api/generate', {
    method: 'POST',
    body: JSON.stringify({ model: 'llama3.2', prompt, stream: false })
  });

  const data = await response.json();
  return data.response.trim(); // returns "1", "2" ... or "unclear"
}

Prompt Engineering Basics

  • Be specific about output format — ask for exactly a digit, not a sentence
  • Give context — tell the model what state the caller is in
  • Handle "unclear" — always have a fallback when the model is not confident
  • Temperature = 0 — for classification tasks, you want deterministic output

Handling AI Delays

Latency Problem Ollama on a small server takes 1–3 seconds to respond. Twilio expects a response within 15 seconds, but the caller experience degrades past 2 seconds of silence. Solution: play a "Please hold..." <Say> while the AI processes, or use regex first and only fall back to Ollama for unrecognised input.

n8n Workflows

What is n8n?

n8n is a self-hosted workflow automation tool — think Zapier but open source and code-capable. Each workflow is a visual pipeline of nodes: webhooks, HTTP requests, code blocks, email senders, etc.

Workflow 1: Quote Engine

Trigger: POST /webhook/quote-engine Input: { service, vehicleType, condition, suburb } │ ▼ [Code Node] — deterministic pricing rules Exterior Wash, Sedan, Standard → base $290 + heavy condition surcharge $40 + SUV surcharge $60 → { quote_min: 290, quote_max: 410 } │ ▼ [Respond to Webhook] → returns JSON to Express

Workflow 2: Quote + Availability (Combined)

Trigger: POST /webhook/quote-and-availability Input: { service, vehicleType, condition, startDate, endDate } │ ├──► [HTTP Request] → quote-engine webhook │ returns { quote_min, quote_max } │ └──► [HTTP Request] → POST /api/availability returns top 3 Calendly slots │ ▼ [Code Node] — combine quote + slots │ ▼ [Respond to Webhook] → { quote_min, quote_max, slots[] }

Workflow 3: Customer Reminder (Scheduled)

Trigger: Cron — every hour │ ▼ [PostgreSQL] — find bookings starting in 23–25 hours WHERE scheduled_start BETWEEN NOW() + 23h AND NOW() + 25h AND status = 'confirmed' │ ▼ [Loop] for each booking: [Twilio SMS] → "Reminder: your Exterior Wash is tomorrow at 9 AM" [PostgreSQL] → INSERT INTO notification_log

Workflow 4: Provider Daily Summary (4:30 PM)

Trigger: Cron — daily at 16:30 AEST │ ▼ [PostgreSQL] — tomorrow's confirmed bookings │ ▼ [Code Node] — format email: count, services, total quote range │ ▼ [Email / SMTP] → provider@shinemobiledetailing.com.au

Common Interview Questions & Strong Answers

Q1. Walk me through what happens when a customer calls your system.
"When the customer calls, Twilio answers the call and immediately sends a POST request to our Express webhook. We validate the request using Twilio's HMAC signature to ensure it's genuine. Then we look up the CallSid in our calls table — if it's a new call, we create a record with state LANGUAGE_MENU. We return TwiML telling Twilio to play our greeting and wait for a keypress. Each subsequent keypress fires another webhook, and we read the stored state to decide what to do next. The entire conversation is a series of stateless HTTP requests tied together by the CallSid."
Q2. How do you handle concurrent bookings — what if two users try to book the same slot?
"We handle this with a conflict check before every INSERT. The SQL query checks for any confirmed booking where scheduled_start < new_end AND scheduled_end > new_start — this is the standard interval overlap condition. If a conflict is found, we return a 409 and the IVR routes the caller back to choose a different time. This is not a perfect distributed lock, but it's safe enough for a single-region deployment with PostgreSQL's row-level locking. For true multi-region scale, we'd use a pessimistic lock or a booking token pattern."
Q3. Why did you choose PostgreSQL over MongoDB for this project?
"Booking data is inherently relational — a booking has a customer, a service, and a business. We need ACID guarantees so a booking is never half-written. PostgreSQL also supports JSONB, which we use for the call's accumulated context — vehicle type, condition, selected slot — without needing schema migrations for every new field. We get relational integrity where we need it and document flexibility where we don't."
Q4. What happens if your server is down when Twilio sends a webhook?
"Twilio will retry the webhook a few times with exponential backoff. Our server also has a /health endpoint that we can use for uptime monitoring. For production, the backend should be deployed with at least two instances behind a load balancer so there's no single point of failure. Because call state is in the database (not in memory), any instance can handle any webhook from any caller."
Q5. How did you secure the webhook endpoint?
"Every request from Twilio includes an X-Twilio-Signature header — an HMAC-SHA1 hash of the URL and POST body, signed with our auth token. Our middleware recomputes this hash and compares it. If they don't match, we return 403 immediately. This prevents anyone who discovers the URL from sending fake call events."
Q6. How does the system support three languages?
"The language is captured in the first step (LANGUAGE_MENU) and stored in the call context JSONB. Every subsequent state handler reads context.language to decide which TwiML to return. The availability slot labels are generated by a dedicated service that formats dates in English, Hindi, and Mandarin. For Hindi and Mandarin, Twilio's <Say language> attribute is set to hi-IN or zh-CN so the TTS engine pronounces the words correctly."
Q7. Why did you use n8n instead of writing everything in Express?
"We separated concerns deliberately. The Express server must respond to Twilio within 15 seconds — it's latency-sensitive. Background tasks like reminder scheduling, email summaries, and multi-step notification pipelines don't belong in the critical path. n8n handles those asynchronously with built-in cron, retry logic, and a visual audit trail. It also means non-developers can tweak reminder timing or email templates without touching the backend code."
Q8. How would you scale this to 10,000 simultaneous calls?
"Three areas: First, Express is stateless — horizontal scaling with a load balancer is straightforward because all state lives in PostgreSQL. Second, the database becomes the bottleneck — we'd use a read replica for lookups, connection pooling via PgBouncer, and caching availability results in Redis. Third, n8n reminder jobs would move to a proper queue (Bull + Redis) so thousands of SMS jobs don't pile up on one n8n instance."
Q9. What is TwiML and how does it work?
"TwiML stands for Twilio Markup Language — it's XML that Twilio reads to control a call. When Twilio sends a webhook to our server, it expects us to respond with TwiML within 15 seconds. The most common verbs are <Say> (text-to-speech), <Gather> (collect DTMF or speech), and <Hangup> (end the call). Our <Gather> element has an action URL — when the caller presses a key, Twilio POSTs their input to that URL, which fires our webhook handler again."
Q10. What would you do differently if you were building this again?
"A few things. First, I'd store timestamps as TIMESTAMPTZ from day one — we had a 5.5-hour timezone bug because PostgreSQL was storing TIMESTAMP WITHOUT TIME ZONE and the Node.js pg driver was interpreting it as local machine time. Second, I'd add a Redis cache for availability slots to reduce Calendly API calls. Third, I'd containerise with Docker from the start so local dev matches production exactly."

Common Fresher Mistakes When Explaining This Project

❌
"I built a voice calling app using Twilio."
Too vague. Interviewers hear this every day. Be specific: "I built a stateful IVR system where call state is persisted in PostgreSQL across multiple Twilio webhook requests."
❌
Listing technologies without explaining why.
Don't say "I used n8n." Say "I used n8n for scheduled background tasks to keep them out of the latency-sensitive webhook path."
❌
Not knowing your own bug fixes.
Interviewers love "what was the hardest bug?" Prepare the timezone story — it shows you understand how PostgreSQL, Node.js, and timezones interact at a systems level.
❌
Claiming AI does more than it does.
Don't say "I used AI to understand speech" if you used regex. It's fine to say "I used keyword matching for now, with Ollama designed in as the next layer." Honesty + a plan is stronger than overclaiming.
❌
Ignoring security.
Always mention Twilio signature validation when explaining the webhook. It shows you think about attack surfaces, not just happy paths.
❌
Not knowing the database schema.
Be ready to draw the ER diagram from memory — businesses → services, bookings, calls; customers → bookings; booking_events as audit log.
❌
Saying "it scales horizontally" without knowing what that means.
Explain that Express is stateless (state is in DB), so you can run multiple instances behind a load balancer without sticky sessions.
❌
Not mentioning the 15-second Twilio constraint.
Every design decision (why DB indexes matter, why n8n is async, why regex beats Ollama for live calls) traces back to this constraint. Lead with it.
Golden Rule for Interviews Every answer should follow: What → Why → Trade-off → What you'd do differently. This structure shows engineering maturity, not just implementation knowledge.
